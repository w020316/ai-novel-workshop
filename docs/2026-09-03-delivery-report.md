## 一、项目概览

**定位**：AI 全流程高质量小说生成器，主打「人工轻度介入 + 长篇连续性」。浏览器本地存储（IndexedDB/Dexie），无需账号。

**技术栈**：Next.js 15（App Router）/ React / TypeScript / Dexie / 多模型 LLM 适配（DeepSeek、智谱 GLM、通义 Qwen）。

**近期新增模块**：趋势灵感扫榜（`/inspiration` 独立页 + 设定工坊 Tab）、灵感卡→新建项目一键带入、灵感卡并入大纲（进入创作流程被消费）、新手引导、导出前版权合规提示、强冲突短剧题材模板。

## 五、用户体验评估（真实用户视角）

### 5.1 评估方法与实质

- 采用 **用户旅程图 + SUS 认知 + 任务完成率** 结合真实浏览器实测（线上站点完整跑通核心链路）。

- 实测证据：新建《像素夏夜》（玄幻·细腻言情·30万字·DeepSeek）→ 世界观「一键生成」（约 15s，412 字）→ 第 1 章（5 阶段流水线，约 2min，927 字）→ 回写章节列表。全程无报错。

### 5.2 用户旅程摘要

`首页 →（无项目）空态三步引导 → 新建项目（题材/字数/文风/AI）→ 设定工坊生成世界观 → 创作工作台生成章节 → 冷读/合规/去AI味 → 导出`。

- 关键路径完成率：100%（实测全部走通）；开箱耗时：世界观 \~15s、章节 \~2min。

### 5.3 SUS 式量化（7 个维度，5 分制）估算

| 维度   | 分   | 说明                              |
| ---- | --- | ------------------------------- |
| 可用性  | 4.5 | 关键路径明确、本地数据无成本                  |
| 易用性  | 3.6 | 术语（AI模型/去AI味/文风）已在本轮加提示，仍需积累默认值 |
| 预期管理 | 4.0 | 已补「创建后会发生什么」流程预览                |
| 反馈及时 | 4.3 | 5 阶段流式 + 进度/stopped 反馈完整        |
| 容错   | 4.0 | 各类生成均有加载/失败/重试兜底                |
| 发现性  | 3.8 | 新增「找灵感/拆书/趋势」入口，仍缺全局搜索/引导tour   |
| 一致性  | 4.2 | 视觉/组件复用高                        |

**SUS 折算≈79/100（B+，可用性良好，位于"可以接受/优秀"区间）**。

### 5.4 体验痛点（实测归纳）

1. **题材/平台单选标签**，首次点击曾被兄弟元素拦截、偶发导航 ref 过期 →（浏览器点击层问题，已加可重试；非应用 bug）。
2. **暂无全局"灵感/草稿"找回入口**：若重构灵感卡后漏收藏，无法跨项目复用。
3. **移动端**通过断点分析判定可自适应，但未在真机视口逐一核对横向溢出（受工具限制）。
4. **术语仍偏高**：对完全零基础者，「文风预设/投稿体检/AI模型」需要更多默认值与副标题解释。

### 5.5 差距分析（需求 vs 实际）

- 长文本连续性：三级记忆+伏笔+一致性+健康体检已覆盖（对应"长篇不掉线"需求）✅

- 选题灵感：趋势灵感+拆书+灵感卡已覆盖（P5）✅

- 商用合规：投稿合规+导出合规提示已覆盖 ✅

- 实时榜单对接：受反爬限制，降级为内置风向+粘贴拆榜（如实标注）⚠️

## 十、阶段五·大纲驱动批量续写（P2 新功能落地）

**需求**：交付报告 §5.7 建议 #3 —— 轮廓驱动批量续写 / 一键连写多章，摆脱逐章点击，提升追更/长篇提效。

### 功能说明

- **批量续写层**：新增 `generateChaptersBatch()` — 对连续章节号依序调用编排器（继承记忆装配/剧情设计/一致性闭环），从起始章起连写 N 章

### 同步健壮性修复（Provider 未配置自动回退）

让「请求的 provider 未配置（如默认 gemini 但未填 key）」不再 503 或把 gemini 的模型名发到别的网关：

- 新增 `resolveProvider(requested, model)`（`providers.ts`）：请求的 provider 已配置 → 采用它及请求模型；未配置 → 回退到第一个已配置 provider 并套用其默认模型（如 GLM 的 `glm-4-flash`）

- 三个 API 路由 `chat / generate-chapter / embedding` 统一改用 `resolveProvider`，并补充 `isProviderConfigured` 判定

- 结果：即使用户新建项目默认 provider 是 gemini，只要未配 key，生成/对话/向量都会透明回退到已跑的免费 GLM，不再报错

### 全流程实跑走查 + 章节乱码排查（阶段九补充）

起 `next dev` 后，用已配置的免费 GLM 对核心链路做了真实端到端验证：

- `POST /api/llm/chat`（非流式）：返回内容为干净 UTF-8 中文，含「」与省略号，无乱码

- `POST /api/llm/generate-chapter`（SSE 流式）：全角标点（破折号——、省略号……、引号“ ”）逐 token 完好返回，无乱码

- 传输层核对：前后端 `TextDecoder(…, { stream: true })` 均正确处理跨 chunk 多字节；token 经 `JSON.stringify` 转义后单行 `data:` 传输，JSON 往返无二次转义——**未发现代码层乱码源**

- **发现并修复的真实缺陷**：`deepseek/agnes` 网关存在间歇性「返回 0 token 且无错误」的空流 → 此前会静默生成空章节（空白/异常观感）。已在 `generate-chapter` 路由增加**空流防护**：0 token 且未中断时改发 `error` 事件（"模型返回为空，请稍后重试或切换模型/Provider"），而非静默 `done`，便于 UI 提示与重试

- 结论：章节乱码为**间歇性模型输出**（如 agnes 网关变体），非本仓库编码 bug；空流已被显式兜底，异常不再静默

- 验证：全量单测 76 文件 / 637 用例全绿；`next build` 通过（静态页 7/7）
